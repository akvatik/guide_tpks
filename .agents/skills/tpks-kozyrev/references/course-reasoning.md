# Разбирать новую ситуацию по материалам ТПКС

Начать с решения, которое предстоит принять пользователю. Выбрать один
существенный для него вопрос и найти в материалах правило или разобранный
пример. Прочитать фрагмент, проверить область его действия, затем сопоставить
с фактами из задачи. В ответе дать вывод, краткое основание и практическое
следствие. Для обсуждения темы это может быть проверяемый сценарий, для
проекта документа — исправленная формулировка, для защиты — один вопрос.

## Как выбрать основание

Все номера страниц ниже относятся к PDF `materials/kozyrev_slides/Vse_kozyrev.pdf`.
Использовать указатели для поиска. Для вопросов за пределами этих двух лекций
искать соответствующий материал через карту задач и указывать его происхождение.

| Что нужно решить | Как применить материал к случаю пользователя |
|---|---|
| За какой результат отвечает ПО? | На с. 25–26 сопоставить требование к системе с условием и сигналом на выходе ПО. Периодичность индикации в примере обеспечивает аппаратура. В новом проекте установить, что наблюдает пользователь, что получает и выдаёт программа и кто обеспечивает остальную часть результата. Обосновать распределение функций сведениями об архитектуре проекта. |
| Можно ли проверить требование? | По с. 20, 22–23 и 27 определить режим, вход и наблюдаемый выход. Подобрать случай, в котором две правдоподобные трактовки дают разные результаты. Для диапазона проверить границу и выход за неё. Порог, таймер и реакцию на сбой брать из задания или обозначать как решение для согласования. Упоминание технологии оценивать с учётом исключения для проектных ограничений на с. 23. |
| Что входит в процесс разработки и что из него выходит? | Установить, какой артефакт поступает, кто его использует, какой документ управляет работой и что появляется в результате. Схема на с. 18 относится к разработке требований к ПО. Перед переносом на другой процесс найти его собственное описание. Для проверки стрелок использовать оригинал схемы по правилам источников. |
| Можно ли изменить принятую версию? | Различать идентификацию версии (с. 31), согласование базовой версии требований и порядок последующих изменений (с. 32). Уточнить, что именно согласовано в данном проекте. При разборе несоответствия выделить наблюдаемую проблему и затронутые единицы конфигурации (с. 65). Планируемые изменения описать в ЗИ по принятому процессу (с. 73–74). |

## Проверить переход от источника к выводу

- Использовать и примеры ошибок самого курса. На PDF с. 28 приведено условие,
  в котором параметр должен одновременно достигать верхней границы и быть
  не выше нижней. При минимуме меньше максимума оно невыполнимо. Это разбор
  логики примера. Для аналогичного требования в работе студента подставить
  реальные границы и проверить значения внутри, снаружи и на границах.
  Выбор включительных границ в исправлении обосновать условием задачи.
- Указать, какой факт из задачи делает правило применимым. Если существенный
  факт неизвестен, дать условный ответ для возможных случаев и назвать,
  какое свидетельство позволит выбрать между ними.
- Различать дефект предъявленного фрагмента и отсутствие сведений в нём.
  По одному требованию можно обнаружить неоднозначность; вывод о полноте
  всей спецификации требует проверки связанных требований (PDF с. 22, 27).
- Если источники расходятся, привести обе позиции и их происхождение.
  Когда есть только студенческий конспект или пример работы, указывать
  именно это основание. Словами «на слайде» обозначать проверенное содержание
  слайда. Собственную интерпретацию формулировать как вывод из этого содержания.
  Например, в `materials/lectures/lectures_konspekt.txt` строка 358 относит
  исполняемый объектный код к выходу кодирования, а строки 489, 494 и 497
  описывают его получение из исходного при интеграции. Для плана проекта
  показать, какой артефакт реально передаётся на сборку, и привести оба
  места как объяснение выбора формулировки. Нормативный вывод потребует
  первичного текста стандарта.
- Когда спрашивают «что скажет преподаватель», дать содержательный вопрос
  к конкретному решению и обосновать его материалом. Приписывать преподавателю
  персональное замечание можно при наличии доступной записи этого замечания.

## Пример переноса на другую предметную область

Учебная ситуация, составленная для пояснения. В музейном киоске приложение
выдаёт контроллеру команду включения подсветки. В черновике написано
«ПО обеспечивает освещённость экспоната 200 лк». Что проверять на приёмке?

На уровне всей системы можно измерить освещённость у экспоната. На границе
приложения по описанной архитектуре наблюдается только команда контроллеру.
Это аналогично распределению поведения между ПО и аппаратурой на с. 25–26.
Для программного требования нужно установить условие выдачи команды и её
ожидаемое значение. Для системного испытания нужны заданные условия измерения
и допустимое отклонение. Число 200 лк взято из учебной ситуации. Если появятся
датчик и обратная связь, заново определить ответственность ПО с учётом этих
интерфейсов. Такой пример пригоден для тренировки, но не служит свидетельством
того, что преподаватель разбирал музейный киоск или утвердил его параметры.
